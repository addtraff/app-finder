# play-radar

Инструмент поиска приложений в Google Play, ежедневного обновления и расчёта метрик
по ТЗ v2.1 и методике «стоит ли копировать приложение» v1.1.

Node.js (ESM) + SQLite (`better-sqlite3`). Никакого бэкенда и сервисов: набор
скриптов-стадий, которые пишут в общую базу `data/radar.db`, и односторонний
HTML-отчёт в `out/`.

## Ключевой архитектурный принцип

**Сырая история не перетирается.** `raw_app_page`, `raw_search`, `raw_reviews`,
`raw_suggest`, `metrics_niche_geo` пишутся с датой и накапливаются. Любой скоринг
пересчитывается задним числом по другим весам — достаточно перезапустить
`score` за нужную дату.

Второй принцип, который спасает ниши от рассыпания между днями: кластеризация берёт
**самую свежую выдачу по каждому ключу**, а не сегодняшний срез. Иначе ниши строятся
из случайной дневной горсти ключей и не сопоставимы день ко дню.

## Установка

```bash
cd "C:\ленды вайбкод\play-radar"
npm install
node src/cli.js init
```

Опционально, для K7 (рекламные библиотеки):

```bash
npm i playwright
npx playwright install chromium
```

## Команды

```bash
node src/cli.js discover --geo US      # полный обход по гео
node src/cli.js daily    --geo US      # ежедневное обновление
node src/cli.js status                 # что накоплено в базе
node src/cli.js stage niche-doors --geo US          # одна стадия
node src/cli.js stage score --geo US --date 2026-09-05   # пересчёт задним числом
node src/cli.js set-policy --app com.example --ok 1      # ручной гейт policy_ok
node src/cli.js record-ads --source meta --app com.example --found 1
```

## Конвейер

```
сбор            collect-charts · harvest-keywords · keyword-serp · enrich-apps
                enrich-reviews · enrich-developer · enrich-permissions · similar-graph
разметка        screen · analyze-pain · check-ads
кластеризация   niche-doors
скоринг         quantiles (geo) · quantiles (niche) · score
вывод           dashboard · export · alerts
```

Каждая стадия перезапускаема с места: берёт только то, чего ещё нет за сегодня.
Поэтому `catchup.ps1` каждые полчаса добирает работу малыми порциями — поиск в Play
жёстко лимитирован (429 уже при двух запросах в секунду, стартовый лимит 20/мин на
выдачу и 60/мин на карточки, при 429 темп ведра автоматически снижается на 30 %).

## Автономность

**Windows** — Планировщик заданий:

```
schtasks /create /tn "play-radar-daily"   /tr "powershell -NoProfile -File C:\ленды вайбкод\play-radar\run-daily.ps1" /sc daily  /st 03:10
schtasks /create /tn "play-radar-catchup" /tr "powershell -NoProfile -File C:\ленды вайбкод\play-radar\catchup.ps1"   /sc minute /mo 30
```

**Linux/VPS** — cron: `run-daily.sh` и `catchup.sh`.

## Конфигурация

| Файл | Что задаёт |
| --- | --- |
| `config/geos.json` | 30 гео, hl, языки отзывов, валюта, тир, `active`, час UTC, справочник доходности |
| `config/seeds.json` | семена: ключи (на языке гео), приложения, категории |
| `config/budget.json` | лимиты обхода и обновления, запросы в минуту по типам |
| `config/institutions.json` | домены и юрлица институций, регулируемые категории, рискованные разрешения, суффиксы региональных клонов |
| `config/scoring.json` | веса prescore, параметры кластеризации, дефолты органики |
| `config/intent-templates.json` | шаблоны интента на 18 языках |
| `config/review-lexicon.json` | регекс-классификатор отзывов на 18 языках |
| `config/schedule.json` | расписание: цикл полного обхода, день облегчённого, периодичность K7, месячные и квартальные задачи, ступени зрелости данных |

`active: true` стоит только у US — это объём приёмки v1. Для v1.5 включите
BR и DE (семена на их языках уже есть). Пороги в конфиге не задаются: **все пороги —
квантили** из `niche_quantiles`, считаются по последнему полному дню.

## Дополнение к ТЗ v2.1 (7 сентября 2026)

Применено поверх основного ТЗ; при расхождении действует дополнение.

| Пункт | Что сделано |
| --- | --- |
| **A1** | `locales_count` заменён на `localized_geo_count`: локализация определяется расхождением `title_hash` или `short_desc_hash` с версией hl=en, gl=US. Дисквалификатор `budget` этапа 2 — «локализовано в больше гео, чем p90 ниши, при возрасте до 2 лет». `locales_apk` — из E4. |
| **A2** | `installs_country` убран. Каноническое `installs` берётся из `installs_source_geo` (по умолчанию US, иначе первое доступное гео из 3.1); дельты и окна считаются только при неизменном источнике, смена — событие `installs_source_changed`. Добавлен `installs_consistency`: расхождение maxInstalls между гео больше 1 % → 0. |
| **A3** | `size_mb` — описательный, заполняется только при объявленном размере. Гейт `heavy_and_bad` срабатывает только тогда; это ожидаемое поведение. Точный размер — `size_mb_apk` из E4. |
| **A4** | `review_lang_mismatch` переопределён: доля отзывов на языках, под которые листинг не локализован. Только уровень A (все 18 языков сняты) и при ≥ 200 отзывов; для B пусто. Уровень A теперь снимает отзывы по всем 18 языкам. |
| **B1** | K7 переписан под Playwright: постоянный профиль, `headless: false`, партии по 90 доменов, пауза 1200 мс, первый 429 — стоп партии и пауза 30 минут с продолжением с места, капча — стоп и алерт. Meta — запрос ровно в два значимых слова, парсинг ссылок `store/apps/details?id=`. Очередь: прирост выше p99 при базе ≥ 50K → уровень A → B по prescore; повтор A раз в 2 недели, B раз в месяц. |
| **B2** | По умолчанию — не разбор APK, а стадия `analyze-tracking`: ищет имя трекера атрибуции (AppsFlyer, Adjust, Branch, Kochava, Singular, Tenjin) в тексте карточки, в тексте privacy policy (отдельный запрос по ссылке из карточки) и в Data Safety — без скачивания файла, полностью автоматически, для всех A/B каждые 30 дней. Находка = прямая улика (`organic=0`); отсутствие находки НЕ считается подтверждённой органикой — текст мог не упомянуть трекер, который реально есть, поэтому это слабее чтения самого APK. `analyze-apk` (чтение реального `apk-import/<package>_<version>.apk`, даёт вдобавок `paywall_sdk`, `compute_location`, `ad_sdks`, `size_mb_apk`, `locales_apk`) остался как опциональный ручной шаг для тех же данных плюс более сильное доказательство отсутствия трекера. |
| **C1** | Добавлен описательный `policy_auto_ok`; очередь и лист «прошли воронку» сортируются им, затем по prescore. Пакетное подтверждение — лист `out/export/e7-политики.csv` и команда `import-policy --file`. |
| **C2** | Команды `import-planner --file` и `import-trends --file` для квартальных выгрузок E1 и E2; листы `keyword-planner` и `trends` в экспорте. |
| **C3** | Считаются `top10_turnover_7d` и `top10_turnover_14d` с пометкой окна; `top10_turnover_30d` появляется на 30-й снимок, при пропусках ставится `partial_window`. |

### K7: запускать в своём терминале

Playwright и Chromium установлены, код готов, но браузер запускается только из обычного
терминала — в песочнице агента бинарь Chromium не исполняется. Первый запуск — дома, в окне:

```
node src/cli.js stage check-ads --geo US --limit 20
```

Профиль браузера лежит в `%LOCALAPPDATA%\play-radarrowser-profile` (переопределяется
`RADAR_BROWSER_PROFILE`): путь проекта содержит кириллицу, а Chromium на Windows с таким
`--user-data-dir` не стартует. Флаг `--headless yes` — для VPS под xvfb.

Селектор карточек креативов в Ads Transparency — единственное место, зависящее от вёрстки
Google. При первом запуске сверьте результат глазами: ровные нули — повод проверить селектор,
а не вывод «все органические».

## Отступления от буквы ТЗ и почему

Каждое проверено на живых данных US — без них конвейер даёт формально правильный,
но бессмысленный результат.

1. **Гейт `broken`.** ТЗ пишет «≥ 1000 оценок». По принципу 9 абсолютные числа запрещены,
   поэтому реализовано как `ratings_count >= p50` гео. Буквально оставлено единственное
   абсолютное правило — «рейтинг выше 4.9 при 10K+ оценок»: ТЗ само называет его
   исключением, потому что оно про шкалу Play, а не про нишу.
2. **`feasibility`** может дать 1 + 0,25 + 0,10 = 1,35. Зажато в 1,0, чтобы `prescore`
   оставался на шкале 0–100.
3. **Пустая компонента скора исключается из взвешенной суммы вместе со своим весом**,
   а не подставляется нулём. Иначе «пусто» превращалось бы в штраф — нарушение принципа 7.
4. **Навигационные запросы.** ТЗ: «название первого результата равно запросу или начинается
   с него → is_brand». В Play первое приложение по `voice recorder` так и называется —
   Voice Recorder. Буквальное правило пометило брендовыми 21 ключ из 160, включая самые
   ценные generic. Добавлено условие единичности: если запрос встречается в заголовках трёх
   и более приложений топ-10, это категория, а не бренд. Стало 2 ключа из 260.
5. **Вездесущие приложения** считаются по вхождениям в **топ-10**, а не в топ-50. По топ-50
   «вездесущим» оказывается почти любое приличное приложение: из 139 ключей вычищалось 77
   приложений — ровно те, что нишу и определяют. По топ-10 вычищается 61 из 241.
6. **`door` считается по сырому топ-10**, без удаления вездесущих: их удаление — приём
   склейки ключей, а не измерение ширины входа. Из расчёта исключены строки, где оценок
   больше, чем установок: это не измерение, а артефакт ограниченного распространения
   (Google Recorder на Pixel отдаёт «1+ установок» при 15 793 оценках и в одиночку
   обнулял `door` ниши voice recorder).
7. **`growth` нормируется по квантилям `growth`**, а не `growth_s`: у них разные шкалы
   (отношение против 0–1), и на квантилях `growth_s` норма схлопывалась в 1,0 у всех.

## Что Play не отдаёт

Раздел «Чего нет в данных» в отчёте перечисляет это по каждому прогону. Кратко:
`locales_count`, `installs_country`, `size_mb` у большинства приложений,
`review_lang_mismatch` при одном языке гео, всё из разбора APK (`attribution_sdk`,
`iap_products_count`, `has_annual_tier`). Эти поля пишутся пустыми, собираются как
описательные и в скор не входят.

`copy_score_gp` равен нулю у всех, пока не выставлен ручной гейт `policy_ok` —
это требование методики, а не ошибка. Для ранжирования очереди используется
`prescore` и `copy_score_provisional`.

## K7 — рекламные библиотеки

Единственный прямой признак закупки. Без `playwright` стадия `check-ads` строит очередь
в `out/k7-queue.csv` в порядке ТЗ (сначала разгоняющиеся > 10 % за сутки при базе от 50K,
затем по `copy_score_provisional`) и не притворяется, что что-то проверила: `ads_found`
остаётся `unchecked`, `organic` = 0,35.

С установленным `playwright` стадия ходит настоящим браузером партиями по 90 доменов
с паузой 1200 мс, капча — стоп и алерт. Селектор карточек креативов в Ads Transparency
зависит от вёрстки Google: при первом запуске сверьте результат глазами, ровные нули —
повод проверить селектор, а не вывод «все органические».

## Экспорт

`node src/cli.js stage export --geo US` кладёт в `out/export/` листы раздела 11:
данные, последний снимок, дельты 7/30, ниши, гео-арбитраж, кросс-гео, кандидаты обхода,
очередь на проверку, размеченная выборка, валидация признаков, квантили ниш, события,
журнал прогонов, воронка, `column_class` (score/descr по каждой колонке).

## Отчёт

`out/report.html` — самодостаточная страница, открывается двойным кликом.
`out/artifact.html` — тот же контент фрагментом, для публикации на claude.ai/code.
`out/report-data.json` — те же данные в JSON.

Разделы: состояние сбора (готовность дня, следующий запуск, зрелость данных, остаток очередей),
план на месяц, сводка по всем 30 гео, разрез по выбранному гео (воронка, ниши, квантили, ядро),
прошедшие воронку с фильтрами, очередь K7, события, границы данных.

План и очереди в отчёте считает `src/lib/schedule.js` — тот же модуль, что и
`node src/cli.js plan`. Нарисованное расписание и реальное совпадают по построению,
а список «осталось добрать» использует ровно те условия, по которым стадии выбирают себе задачи.

Локальный просмотр с сервера, если файл открывается не двойным кликом:

```bash
node tools/serve.js 8777
```
